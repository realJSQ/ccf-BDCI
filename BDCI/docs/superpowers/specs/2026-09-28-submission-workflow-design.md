# 从验证闭环到正式参赛作品

状态：设计草案，待确认；尚未实施新的研究方法或追加模型调用。

## 目标和既有约束

保持完整目标：改进方法，完善基于 JiuwenSwarm 的自动科研流程，最终形成满足赛题的可提交作品。保留 Agent 自动提出论文题目、用户当前电脑加模型 API、轻量 Tectonic、官方代码来自 AtomGit、GitHub 用于协作等已确认选择。停止基础模型能力和算术难度校准，不重写历史负结果。

自动科研能力和论文贡献是两件相互衔接的工作：系统必须能完成选题到论文，论文必须对一个明确的 Agent 研究问题提供可信证据。最终课题仍由选题 Agent 根据文献和实验能力提出，不能将开发者建议改写成“Agent 自主发现”。

## 路线比较

1. **推荐：完善研究证据验证与失败恢复能力，让选题 Agent 研究其有效性边界。** 在同一原生框架内提供多种 CPU 科研任务、版本化实验产物和可计量恢复策略，研究跨阶段错误如何影响最终报告、修复是否值得。与框架贡献直接关联，避免继续测模型算术能力；需要强传统基线，不能仅以规则拦截率自证。
2. 继续同伴建议策略：增加独立初答、无 peer 对照和跨任务重复。更接近旧 pilot，但相关文献密集，模型调用多，普通提示改写不具备已证实的新颖性。
3. 仅完善文档与外审：能补交付形式，无法弥补当前研究证据，因此不作为正式作品路线。

推荐的是实验能力和系统推进路线，不是预先指定论文结论。Agent 可以否决候选或提出其他可执行问题；所有筛选理由保留。

可交给选题 Agent 审查的候选问题是：在科研工作流允许合法更新、存在复合证据污染时，哪些验证与恢复策略能在固定预算内提高正确完成率？潜在论文价值来自可复现测量、强基线比较和边界分析；尚未确认新颖性或收益。

## 自动流程与模块边界

沿用 Swarm Skill + 原生 SwarmFlow + TeamWorkerBackend，不新增替代框架。

1. 文献模块保留元数据、全文可得性、被支持的具体主张及来源版本。无法取得全文必须标记，不能将摘要推断包装成全文核对。
2. 选题 Agent 提出至少两个可证伪候选，Critic 对近邻重合、可执行性、强基线、预算和负结果解释进行审查。候选不通过时有界修订，禁止无限搜索或强行通过。
3. 实验计划包含数据/工作流划分、指标、对照、消融、样本和预算；先存档哈希再执行。开发集与保留集按工作流/故障组合分开，不能看完保留结果继续调方法后声称独立验证。
4. CPU 实验适配器提供可复现产物，例如分类指标聚合、优化统计、排队仿真；模型负责设计、分析和写作。执行器和评分 oracle 分离，不向被测 Agent 泄漏正确标签。
5. 在源码 Rail 中实现可复用的实验身份与版本约束；版本绑定、依赖失效、恢复控制分开。范围限可机械检查的关系，不宣称验证所有科学语义。
6. 结果分析输出完成率、错误与资源数据。结构化数值表从可信记录生成；模型解释需要引用对应证据。保留失败、拒绝和负结果。
7. Writer → Reviewer → Reviser 使用通用实验报告，而非绑定旧 pilot。限定修订次数；检查不仅看有没有改字，还要核对数值、引文支持和未解决的重要问题。
8. 冻结 PDF 与摘要哈希，再接外部 ICLR 审稿。论文改变后需重新建立与 Token 的对应关系。最终打包检查完整要求，任何硬缺项不得标为 submission_ready。

## 实验质量与对照

候选方案批准后由 Agent 给出预注册的具体样本规模与阈值。最低设计要求：

- 至少三个工作流类型，包含清洁输入、合法更新和错误输入；复合错误应与单一错误分别报告。
- 对照包括提示约束、schema、内容哈希、强类型与来源验证，以及完整重跑。完整方案包含不修复的阻断消融；所有策略接收相同可用信息。
- 故障注入器与检测器独立实现；评分依据预先定义的数据语义，不能直接拿门禁是否接受当科学正确性标签。
- 主指标是正确完成率；并列报告最终数值错误、误拒绝、恢复成功、重执行量、tokens 和耗时。拒绝所有任务不算成功。
- 以工作流实例为配对/重采样单位，区分多个模型请求与独立样本。报告区间及失败个案，不将大批重复字段当独立证据。
- 若强基线相当、误拒绝上升或恢复比完整重跑更贵，保留该结果并收缩主张；不得通过换指标或选择结果制造改进。

## 预算、错误处理与恢复

首个新研究 campaign 最多 24 次模型请求，每次输出上限 3,200 tokens，累计返回 usage 达到 100,000 tokens 后停止后续请求。该 usage 阈值是后反馈停止条件，不是严格费用上限；单次请求可能跨过阈值。旧账本不清空，不增加 SDK 自动重试。正式实验规模必须在先验计划中另行冻结，不能自动扩大预算。

请求已发出但结果状态不明时不盲目重发；从凭据和日志确认。结构或语义失败单独记录；最多一次有预算的修复，修复消耗计入对应策略。离线 fixture 只能证明软件流程，不进入真实模型研究结果。

资源账本分别记录历史开发、当前候选、最终正式运行、恢复和外审。保留 API usage、阶段时间边界、执行器 wall time、峰值内存和机器信息；不知道费用时明确未知。

## 实施顺序与正式完成条件

1. 保存本次差距审查、近邻阅读和资源审计；确认设计。
2. 通用实验报告与证据身份契约、受控实验适配器、来源绑定和恢复机制；执行必要软件测试与真实框架离线集成。
3. 运行有界自动候选提出和 Critic；冻结可证伪设计，再进行真实方法比较。基础模型能力不另开测试。
4. 根据证据完善方法；预注册正式保留集验证、消融和失败分析；不得只复制开发集结果。
5. 自动生成完整英文 ICLR 论文，图表与引用可追溯；审稿、修订、PDF 文本与视觉检查。
6. 完善架构/调用/创新/资源文档、源码 patch 和官方贡献 PR 材料；在干净环境验证安装、离线复现与生成物一致性。
7. 收口团队名、官方样例和当轮要求、最终外审 Token、贡献 PR 链接；按团队名生成 ZIP，完整验收后才可宣称可提交。

## 设计自审

- 自动选题仍由 Agent 提案，不把开发建议当作已产生的 Agent 决策。
- 数据真实性、门禁完整性、语义正确性、科学新颖性分别验收，不互相替代。
- 正常更新与误拒绝进入实验，避免只有人为违规样例。
- 外部账号信息留到可审查材料完成后收口，不阻断当前本地工作。
- 新预算仅覆盖首轮；正式规模尚需 Agent 在结果出现前提出和冻结，不隐式授权无限开销。
