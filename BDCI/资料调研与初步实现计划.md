# 资料调研与初步实现计划

日期：2026-09-28。状态：调研结论与候选方案，尚未实施或批准为最终设计。

用户已确认实验资源为「当前电脑 + 模型 API」。本轮只阅读资料并编写计划，不修改业务源码、Git 配置，不提交或推送。

## 1. 结论

建议以 **Swarm Skill + SwarmFlow** 作为候选执行基础：团队技能规定职责，SwarmFlow 固定执行步骤，现有科研模块承担可复用任务。科研证据 Rail 仅是候选源码增量，是否优先实现，应由论文选题、预实验和对评分的实际作用决定。先筛选有研究价值且可验证的 Agent 课题，再完成真实闭环。

这不是已经验证成功的科研系统。此前仅验证了安装、构建和服务启动；模型、检索服务、LaTeX 和真实科研流程仍待验证。

### 竞赛导向校准

本项目以比赛有效性与四维评分为验收依据。环境启动和 PDF 编译只是中间里程碑，不能视作参赛作品完成。以下评分依据本地保存的赛题页，未声称已核实最新公告。

| 维度 | 初赛权重 | 工作重点 | 验收材料 |
| --- | --- | --- | --- |
| 论文质量 | 60：Stanford Reviewer 40 + 论文评测 Agent 20 | 先做选题与新颖性判断；严谨实验、充分基线/消融、清晰分析与可信引用；审阅反馈用于修正真实问题 | Agent 生成的英文 ICLR PDF、实验原始材料、对应官方 Access Token |
| Agent 系统能力 | 15 | 从研究目标到论文的自动衔接、真实工具执行、失败处理；说明人工干预边界 | 可运行源码、架构/模块调用/创新文档、运行轨迹和复现指南 |
| 资源消耗 | 10 | 有限预算、小规模预实验、复用中间产物、控制无效迭代；评价相应质量下的资源消耗 | 可追溯 Token/时长日志、资源报告；未知费用不伪造 |
| openJiuwen 贡献 | 15 | 必须修改 JiuwenSwarm 源码；选择有实际价值、可复用、可验证的改进 | 源码差异、必要测试与文档、贡献说明和 PR 链接；保留 patch |

源码修改还是作品有效性的硬门槛，不只是争取 15 分的可选项。即使采用单 skill 路线也必须满足。不能为满足门槛只改无关文字，也不能预设“增加一个 Rail 就能拿满贡献分”。

复赛仍为 60/15/10/15，但论文 60 分细分为自动评审、专家评审、长文生成与跨主题泛化各 20；资源效率以现场复现为依据。因此首版聚焦一个课题，同时将领域假设与流程分离，为后续跨主题验证留出接口，不将系统硬编码成单篇论文模板。

**调整后的推进顺序：**补读 FARS 原始资料并核实比赛阶段/样例 → Agent 方向候选课题与文献差距分析 → 成本可控的预实验 → 确定论文问题和有助于结果的源码贡献 → 自动科研闭环 → 正式实验与审阅 → 完整提交材料。

FARS 目前只读过比赛页介绍，尚未独立调研其原始资料。应补查研究筛选、实验调度、失败处理、负结果呈现、自动写作及资源取舍；其示范规模不是本项目必须复制的规模。

## 3. 比赛目标与工程目标

比赛硬要求详见 [任务要求](任务要求.md)。关键是：必须修改 JiuwenSwarm 源码；交付英文 ICLR PDF、完整 Agent 工程、复现与资源报告、贡献材料及与论文对应的 Reviewer Access Token。

评分重点是论文质量 60%、系统能力 15%、资源消耗 10%、框架贡献 15%。因此需要两条相互衔接的工作线：

1. **系统线**：建立能研究、做实验、留存凭据、写论文的 Agent 工作流。
2. **科研线**：提出可检验的问题，设计公平实验，得到真实结果并形成论文。工程模块存在并不自动构成论文创新。

当前电脑适合承担编排、代码执行、小规模 CPU 实验、统计及 PDF 编译；推理走外部 API。首版不规划本地训练大模型、分布式集群或批量生产多篇论文。

用户随后授权使用 `BDCI/apis.txt`。已脱敏检查，文件提供 DeepSeek 接口说明、候选模型名和凭据，并明确要求控制用量。密钥不写入计划、源码、日志或提交材料。本轮没有发起收费模型调用；文件内列出的模型名是否可用需在接入时核实。后续连通检查建议最多 3 次请求（含重试）、单并发、每次限制输出；正式实验另设聚合 Token/时间/重试上限，禁止无上限循环。

## 4. 现有能力与真实边界

### 4.1 Team 与 Swarm Skill

标准团队技能包含 `SKILL.md`、`roles/*.md`、`workflow.md`、`bind.md`、`dependencies.yaml`。角色需要职责、成功条件、边界和输出格式，而不是只有一个角色名称。

官方已有研究团队示例，包含协调、调研、写作、审阅，并允许审核退回。参见 [SwarmSkills](jiuwenswarm/docs/zh/SwarmSkills.md) 与 [AgentTeam](jiuwenswarm/docs/zh/AgentTeam.md)。

### 4.2 SwarmFlow 编排

已有 Python 工作流脚本机制，入口为 `META` 和 `async def run(args)`，提供 `agent`、`agent_session`、`parallel`、`pipeline`、`phase`、结构化 `schema` 以及共享 `budget`。团队技能可携带 `scripts/workflow.py`，无需再实现一套调度器。

需要明确处理两个边界：`parallel` 的失败项可能返回 `None`，不能过滤后直接宣布阶段成功；文档说明预算耗尽后工作流失败且不能直接断点续跑。因此首版只承诺保存已完成产物与可重跑阶段，不承诺恢复任意进行中的会话。参见 [SwarmFlow 指南](jiuwenswarm/docs/zh/TUI使用SwarmFlow指南.md)。

### 4.3 Harness 与 Rail

Harness 管理 Agent 的任务循环、工具、状态、上下文和停止条件。Rail 是生命周期扩展点，可以在模型或工具调用前后执行逻辑。现有框架已经有预算停止、循环检测、权限控制、轨迹采集、技能加载及验证机制，不应把这些全部重写成参赛创新。[Harness 文档](jiuwenswarm/docs/zh/Harness.md)

源码入口：

- `jiuwenswarm/agents/swarm/providers/member_rails.py`：团队成员 Rail 装配。
- `jiuwenswarm/agents/swarm/providers/builtin_rails.py`：内置 Rail 描述和发现。
- `jiuwenswarm/agents/harness/common/plugins/rail_manager.py`：外置 Rail 导入与生命周期管理。
- `jiuwenswarm/agents/harness/common/rails/stream_event_rail.py`：模型和工具事件投影。

仅制作一个仓库外的插件不足以清楚满足本题源码修改要求；拟将通用科研凭据能力及注册、配置、测试放进 JiuwenSwarm 源码，并保留可审查的差异。

### 4.4 已有 autoResearch / PAPER provider

默认真实路径是 `provider_factory.py` 装配已安装 agent-core 中的 `PaperArtifactProviderImpl`，不是同目录名字相似的 `PaperProvider`。安装包确实包含课题调研、实验设计、代码/实验执行、反思、报告和 LaTeX 相关模块。

必须区分：

| 路径 | 已核实情况 | 不应假定 |
| --- | --- | --- |
| 默认 `PaperArtifactProviderImpl` | 接受空的初始论文路径，支持启动和暂停；`resume()` 明确返回 `SCENARIO_NOT_SUPPORTED`；task 到 run_dir 的索引在内存中 | 不能宣称进程重启后可自动续跑 |
| 可注入的旧 `PaperProvider` 桥接 | 调用 ManagerRuntime，含用量账本和产物汇总；它自身不支持暂停/恢复，并有模型环境相关串行锁 | 不能用这条路径的限制代表默认 provider 的全部行为 |
| 报告编译 | 有 LaTeX 发现、预检、编译代码 | 不会自动安装 TeX；默认 article 前导不是已核实的 ICLR 模板 |

另一个关键风险是调用链覆盖：Team 成员装上的 Rail 不一定能观察独立 autoResearch 内部的所有模型和工具调用。必须先测覆盖，再决定采用整条 provider 还是只复用其模块；不能将两个执行引擎同时作为主调度器。

源码依据：

- [默认装配](jiuwenswarm/jiuwenswarm/agents/harness/common/rsi/provider_factory.py)
- [可注入桥接](jiuwenswarm/jiuwenswarm/agents/harness/common/rsi/paper_provider.py)
- 默认实现：`.venv/lib/python3.13/site-packages/openjiuwen/rsi/artifact_rsi/paper_opt/auto_research/tree_provider/provider.py`
- 编译与默认文档：上述包的 `modules/reporting/latex_runtime.py`、`latex.py`。

### 4.5 资源与轨迹

已存在模型用量、工具事件及 OTLP 归档能力。普通诊断数据库有保留期限，不能把它当作比赛永久证据。计划复用现有统计并定期导出科研运行档案；Token 缺失时标记未知，费用没有可信价格或账单时不填伪精确数字。

## 5. 路线比较

| 路线 | 优点 | 局限 | 定位 |
| --- | --- | --- | --- |
| 单 skill + 最小源码扩展 | 易于快速跑通，调用量较易控制 | 复杂阶段相互影响，独立审核弱 | 基线和紧急缩减方案 |
| **Swarm Skill + SwarmFlow + 科研证据 Rail** | 分工、顺序、输出与验收明确，能形成独立源码贡献 | 需验证成员事件覆盖与结构化工具契约 | **推荐主线** |
| 直接采用完整 RSI PAPER provider 并扩展 | 可能最大程度复用现成科研能力 | 恢复、ICLR 输出、内部调用覆盖和资源约束尚需验证 | 第一阶段小样本对照验证后再决定是否采用 |

路线选择以最小验证结果为准，不预先认定多 Agent 或现成 provider 一定更好。

## 6. 任务框架与流程

```text
研究目标、预算、数据限制
  ↓
环境预检：模型 / 检索 / 数据 / 编译器
  ↓
文献检索与来源核验 → 文献表、相关工作、已有方法差距
  ↓
候选假设与可行性筛选 → 固定研究问题和评价指标
  ↓
实验计划 → 基线、主方法、消融、数据划分、随机种子
  ↓
代码与最小实验 → 先确认指标与执行链正确
  ↓
正式实验与结果归档 → 原始输出、退出状态、版本与资源记录
  ↓
结果核验与统计 → 成功、失败、负结果及不确定性
  ↓
英文 ICLR 写作 → 从核验过的表格/图和来源记录生成
  ↓
独立审阅与有限返工 → 必要时回到设计或实验
  ↓
本地验收 → PDF、引用、复现命令、材料清单
  ↓
冻结论文 → 官方 Reviewer → 对应 Token → 最终提交包
```

全流程由预算和运行档案贯穿。失败可修复时返回所属阶段，耗尽预算时保留部分结果并明确失败；不能用编造的实验数值补齐论文。若官方评审后修改论文，需要重新核对 Token 是否仍与提交版本对应。

建议五种逻辑职责：协调者、文献研究员、实验工程师、论文作者、独立审阅员。逻辑角色不等于五个常驻进程，初始最多并发 2 个 API worker；审阅员不参与自己正在审核的实验结果修改。

每个阶段只读取所需产物，避免把全部聊天历史重复传给每个角色。关键产物包括文献表、实验计划、运行清单、原始指标、结论与证据映射、论文源文件、资源账本。

## 7. 拟新增的最小实现

### 7.1 ResearchEvidenceRail 与结构化工具

名称为暂定。主目标是把“我做过实验”变成可检查的文件和记录。

- 实验工具返回结构化凭据：`run_id`、数据/代码版本、配置、种子、命令、退出码、指标文件、开始结束时间及文件 hash。
- Rail 校验并登记这些凭据，避免从任意 Bash 文本猜测实验是否成功。
- 维护 `论文结论 → 指标 → 实验 → 原始产物` 的关联；实验失败或证据缺失时，拒绝通过相应验收。
- 文献检查区分元数据存在、引用键有效、内容是否支持主张。前两者可较多自动化，第三者只能结合原文和独立审阅，不能保证由 Rail 自动证明科学真实性。
- 汇总既有用量事件，补齐实验运行时间与实际可采集的内存等信息，并永久导出。

阶段完成和打包需调用实际验收逻辑，不能仅靠提示词要求“请诚实”。通用 shell 或其他 provider 可能绕过某个工具钩子，因此最终产物验收必须独立执行；缺少凭据的产物不能被纳入已验证结果。

### 7.2 职责边界

Swarm Skill 管角色与协作约定；SwarmFlow 管阶段和分支；科研工具管真实操作；Rail 管调用边界的登记和校验；最终验收器管交付是否完整。预算首先复用上游机制，恢复首先采用产物级重跑，首版不新增一套通用预算或恢复框架。

## 8. 初步实现阶段及验收

| 阶段 | 工作 | 验收标准 |
| --- | --- | --- |
| P0：竞赛与研究可行性 | 补读 FARS 原始资料、核实比赛阶段和样例；筛选 Agent 课题；固定版本并验证现有接口和调用链；接入模型后做受限预实验 | 课题有可说明的文献差距和可执行实验；画清调用链，选定执行路径与源码增量 |

## 9. 初步科研方向与评测设计

未定案候选问题：**预算受限时，显式实验凭据和阶段验收能否提高科研 Agent 的可复现完成率，并减少无证据结论？** 适合当前电脑 + API 的资源条件，也与候选实现能力一致；但新颖性尚未经过系统文献检索验证，不能直接写成论文贡献，更不能为了证明预先选定的 Rail 而倒推选题。需与其他 Agent 前沿课题比较研究价值、实验可行性和成本后再定案。

候选对照：单 skill、无新增证据 Rail 的 Team skill、加入证据 Rail 的同一 Team skill；两种 Team 条件尽量保持相同角色、提示词、编排、工具和预算，仅改变目标机制。再做去掉证据校验、去掉阶段验收的消融。先不要同时引入动态模型路由、自演进和新的调度算法，否则难以归因。

建议指标：

- 可复现完成率：独立重跑通过的任务数 / 全部任务数。
- 交付覆盖率与失败率：防止系统只拒绝输出就获得很低的错误率。
- 无证据主张率：按预先固定的标注规则审查事实/数值主张，不能只看 Rail 自己给的分数。
- 引用错误率：区分文献不存在、元数据错误、内容不支持。
- 质量—成本关系：同一 Token 上限下的质量，以及相近质量下的用量和耗时。

先用少量任务做连通与成本试验，再依预算确定正式样本量、重复次数与置信区间。测试任务与调试任务分离；保留负结果和所有失败，不在看到测试结果后反复更改评价口径。最终 Reviewer 成绩只是一项外部评价，不替代真实实验。

如检索发现上述方向已有充分相似工作，应在正式实验前调整问题，例如缩小到实验结果与论文数值一致性，而不是硬称已有工程机制为新算法。
