  "title": "Agent-Originated Recovery Plans Under Selective and Full Replay: A Development-Only Paired Study",
  "abstract": "This development-only study asks how replay policy changes correct completion and tool work when the same model-proposed recovery plan is replayed against a six-node fork/join workflow after a legitimate source update, with and without a missing declared dependency. Six self-authored base instances span tabular, retrieval, and classification families; each is paired across clean, update, and incomplete-lineage scenarios and four policies (A, B, C, D), yielding 18 completed model plans and 72 CPU policy replays. Under the preregistered strict interface, clean scenarios completed correctly in all 24 replays with zero tool calls; update scenarios produced 4/6 correct completions and 2/6 non-completions per policy, with C doing 24 tool calls versus 16 for A, B, and D; incomplete-lineage scenarios produced 0/6 correct completions and 6/6 non-completions per policy, all attributed to missing terminal action. A post-hoc terminal normalization that appends emit after an existing final rerun(report) changed 8 plans and raised all cells to 6/6 correct completion, but this is not a preregistered success, held-out confirmation, or equivalence result. Selective replay did not outperform the model's own plan on these data; full replay did extra tool work. No transient errors were injected, so B is an error-only negative control expected to match A. The malformed plans are not voluntary refusals; the same plan is replayed across policies. Tools perform calculations, so this is not a model arithmetic test. We describe useful negative evidence and system engineering in JiuwenSwarm native orchestration with bounded request accounting, without claiming a new algorithm, broad robustness, or scientific novelty.",

      "text": "Agentic workflows increasingly execute multi-step tool plans over mutable sources. When a source changes, a central engineering question is how much of the prior plan must be replayed: only the nodes the model requested, or a broader closure that includes declared dependents. Prior mechanisms for selective invalidation and version lineage already exist, so the contribution here is not a new attribution algorithm. Instead, this development-only study examines how replay policy interacts with recovery plans that the model itself proposes. The research question is: for the same model recovery plan and visible tool receipts, how do full versus declared-dependency replay change correct completion and tool work on source updates, with and without a missing dependency? The hypothesis, refined during protocol design, is that with complete declared lineage selective and full replay should produce the same current artifact with less work when an unaffected branch exists, while with missing lineage selective replay can leave stale output unless the model plan explicitly repairs the missing path. Full replay may improve correctness at extra work. These mechanisms are prior art; the study tests their interaction with model-proposed recovery plans. The workflow is a concrete six-node fork/join graph: read_main -> summarize_main -> combine -> report, and read_aux -> summarize_aux -> combine. In the incomplete-lineage scenario the declared edge summarize_aux -> combine is removed. Healthy cached receipts are generated at source v1; the source update and declared-edge omission are applied before the recovery-plan model sees the observation. Both updated scenarios present exactly the same current source values, and no mid-request source changes occur. Four policies are compared. A executes model reruns in listed order. B is A plus one transient retry. C unions requested nodes with all nodes after any source change. D unions requested nodes with the changed source and declared transitive dependents. C and D deduplicate and topologically order work, and all policies honor model refusal. Work caps include attempts; emit does not consume a tool call and emits the cached report. The same plan is replayed across policies, so differences reflect policy rather than plan variation. The malformed plans observed here are not voluntary refusals; they are missing terminal actions. Six self-authored base instances are the unit of analysis, and the 72 CPU runs are repeated measures, not independent samples. No heldout or significance claim is made, and no broad robustness or novelty claim is supported. Tools do the calculations, so this is not a model arithmetic test. The implementation uses JiuwenSwarm native orchestration and bounded request accounting, but that is system engineering rather than scientific novelty.",
